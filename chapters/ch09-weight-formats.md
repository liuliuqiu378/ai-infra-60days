## 1. 序列化三件套：从 pickle 到 safetensors

### 1.1 老答案 torch.save（pickle）：能用，但又慢又危险

深度学习框架的祖传方案是 Python pickle：把整个 Python 对象图（张量、类、甚至
代码引用）序列化进文件。两个致命问题：

1. **反序列化会执行任意代码。** pickle 的数据流里可以嵌入 `__reduce__` 回调，
   你加载一个"模型"，等于运行一份来路不明的脚本——HuggingFace 仓库里一个
   恶意 .bin 就能让你的训练机沦陷。这就是 safetensors README 里 "safe (as
   opposed to pickle)" 的含义（来源：huggingface/safetensors，2026-10-16）。
2. **必须整体构造对象图才能拿到第一个张量。** 加载 = 解析对象、建 Python 对象、
   再分配显存搬运，没法只读一个张量，也没法把文件直接映射进内存。

历史上大量 `pytorch_model.bin` 就是 pickle 的产物。今天 HuggingFace 已把
safetensors 设为默认分发格式，`.bin` 属于遗留兼容。

【类比】pickle 是"把整个房间连家具带杂物打包进一个箱子，拆箱必须从第一件拆到
最后一件"；safetensors 是"先给你一张 32KB 的货物清单，每件货在箱子里的编号
位置写得清清楚楚，要哪件直接伸手拿哪件"。

### 1.2 safetensors：8 字节 + JSON + 纯数据，三段式

官方规范（huggingface/safetensors README / PyTorch projects 页，2026-10-16）：

```
[8 字节]  little-endian uint64：后面 JSON 头的字节长度
[N 字节]  UTF-8 JSON 头：每个张量名 → {dtype, shape, data_offsets:[start,end]}
[剩余]    纯二进制数据区：所有张量紧密排列的裸数值，小端序，无压缩
```

JSON 头里**只有数值张量的描述，没有任何可执行内容**——这就是安全性的来源：
加载器只能做"按偏移读字节、按 dtype 转张量"这一件事。而 `data_offsets` 让
mmap（内存映射）零拷贝成为可能：操作系统把文件按页（4KB）映射进进程地址空间，
程序访问到哪一页，内核才从磁盘拉那一页——**读一个张量不再要求先解析整个文件**。

**实战观察（本地实测，2026-10-16）**：`python code/ch09/parse_safetensors.py`
只读前 8+32,280 字节，解析本机 Qwen2.5-0.5B（bf16）的 model.safetensors：

| 观察项 | 实测值 | 你能看出什么 |
|---|---|---|
| 文件总大小 | 988.1 MB | 0.5B 模型的 bf16 裸权重 |
| JSON 头 | 32,280 字节，占全文件 **0.003%** | 拿清单的成本几乎为零 |
| 张量数 / 类型 | 290 个，全部 BF16 | 清单完整可枚举 |
| 总参数 | 494,032,768 | 与 HF 卡片 "0.5B" 严丝合缝 |
| 数据区 | 988,065,536 B = 494,032,768 × 2 | **零 padding、零包装开销** |
| offsets 连续性 | True | 张量紧挨排列，可整体 mmap |
| `__metadata__` | `{"format": "pt"}` | 唯一的键值元数据：来源框架 |

整个模型 = 清单 + 裸数字，没有第三样东西。这也解释了为什么 safetensors 文件
**没法单独装分词器、chat template、模型配置**——那些 JSON 得和 config.json、
tokenizer.json 一起通过 `snapshot` 目录分发，于是有了下一个格式。

【坑】"能 mmap"不等于"你会用到"：`torch.load`/`from_pretrained` 默认可能把
数据整体读进内存再分配显存；只有加载器显式走 lazy/低内存路径（或你用
`safetensors.safe_open` 手动按 key 取）才吃到 mmap 红利。判断依据永远是
I/O 量和首 token 延迟，不要假设框架替你做了优化。

### 1.3 分片与 index：大模型文件不是一整块

HuggingFace 的规则：单个 safetensors 超过 5 GB 会切片，于是出现
`model-00001-of-00002.safetensors` 和一份 `model.safetensors.index.json`——
index 里是"张量名 → 所在分片"的映射表（本质就是把 JSON 头提升为独立索引）。
加载器读 index、按需打开分片。这和 GGUF"单文件大一统"形成路线对比（第 2 节）。

## 2. GGUF：为"一个文件跑起来"而生

### 2.1 结构逐字段（ggml 官方规范 docs/gguf.md，2026-10-16）

```
魔数 "GGUF" (4B) | 版本 u32 | 张量数 u64 | KV 元数据数 u64
→ KV 对序列（每对：key 字符串 + 值类型 + 值；类型涵盖 u8/u32/u64/f32/bool/数组/字符串）
→ 填充对齐到 general.alignment（默认 32 字节，0x00 填充）
→ 张量描述符 × 张量数（名字、维度数、每维 shape、ggml_type、数据偏移）
→ 张量数据区（按对齐排布）
```

三个设计差异让它成为边端之王：

1. **元数据是类型化的 KV，不是自由 JSON。** 每个值自带类型标签（数组、字符串、
   整数），C/C++ 解析没有 JSON 依赖——llama.cpp 是 C++ 项目，GGUF 天生为
   "不用解析器也能读"设计。
2. **分词器整个住进文件。** vocab、merge 表、special tokens、chat template 全是
   KV——`llama-cli -hf repo:Q4_K_M` 一条命令拉一个文件就能对话，因为"模型"
   和"说话方式"不再分家。
3. **张量可以直接按量化类型存。** safetensors 的 dtype 是 F16/BF16/I8 这类规整
   枚举；GGUF 的 ggml_type 有整套量化家族（Q4_0、Q4_K_M、Q6_K、IQ2_XXS……），
   量化在**文件格式层**就是一等公民——这正是第 5 节 k-quants 生长的土壤。

GGUF 2023-08-21 由 Georgi Gerganov 发布（替代 GGML/旧 GGJF），是 llama.cpp /
ollama 生态的通用载体；今天 vLLM、Ollama、LM Studio、Jan 等也已支持读取 GGUF
（vLLM 支持矩阵见第 6 节）。

### 2.2 一张对照表看懂"格式"这个维度

| 维度 | safetensors | GGUF | 旧 .bin (pickle) |
|---|---|---|---|
| 出身 | HuggingFace | llama.cpp/GGML | PyTorch 早期 |
| 头部 | 8B + JSON | 魔数 + 类型化 KV | pickle 对象流 |
| 安全性 | 仅数值，防代码执行 | 仅数值+KV | **可执行任意代码** |
| 分词器/模板 | 外部文件打包 | **单文件内置** | 外部文件 |
| 量化类型 | 全精度+规整 INT8 等 | **k-quant 全家族原生** | 规整 |
| 加载方式 | 可 mmap 零拷贝 | 按需 seek + 转换 | 整体构造对象图 |
| 主战场 | HF Hub、vLLM/TensorRT-LLM/SGLang | CPU/边端/消费卡、ollama | 遗留兼容 |
| 分片 | >5GB 自动分片 + index | 单文件不分片 | 依框架 |

**决定加载速度与内存占用的不是文件名后缀，是这三行**：① 数据是否能 mmap 按页
懒加载；② 是先读完整清单还是先构建对象图；③ 量化数据是否与推理 kernel 的
内部布局一致（不一致就要加载后现转换——第 8 节的坑）。

【坑】**格式 ≠ 精度，两条独立的轴。** GPTQ 和 AWQ 的量化模型**也是
safetensors 文件**（int4 + scale/qweight 张量）；GGUF 里既有 Q8_0 也有原始
f16。看到 .safetensors 不代表"全精度"，看到 .gguf 也不代表"4-bit"——打开
header 看 dtype 才算数。下一节先把"精度"这条轴讲清楚。

## 3. 数值格式：小数点住在哪几位里

### 3.1 浮点的三段式

所有浮点格式都是 `(-1)^符号 × 2^(指数-偏置) × (1+尾数)`。位宽重新分配给
指数和尾数，就得到一张此消彼长的表（FP32/TF32/FP16/BF16 数据为 IEEE 754/
NVIDIA 公开规格；FP8 为 OCP OFP8 Rev 1.0，2023-12-01，经 NVIDIA 官方文档核实）：

| 格式 | 符号/指数/尾数 | 范围（可表示） | 特点与用途 |
|---|---|---|---|
| FP32 | 1/8/23 | ±3.4×10³⁸ | 训练数值稳定基准 |
| TF32 | 1/8/19 | 同 FP32 | Ampere+ TensorCore 内部精度，进出仍 FP32 |
| FP16 | 1/5/10 | **±65,504** | 尾数最多=精度最高，但范围窄，梯度易溢出 |
| BF16 | 1/8/7 | ±3.4×10³⁸ 量级 | 指数同 FP32=永不溢出的动态范围，牺牲尾数 |
| **FP8 E4M3** | 1/4/3 | **±448**（bias 7） | 尾数多一点，**前向权重/激活**默认 |
| **FP8 E5M2** | 1/5/2 | **±57,344**（bias 15） | 范围同 FP16 量级，**梯度**默认 |
| INT8 | 整数 | 对称 ±127 / 非对称 0–255 | 带 scale 仿射映射回实数 |
| INT4 | 整数 | 0–15 | 16 个格子，必须配 scale |

两条工程结论直接从表里读出来：

- **训练选 BF16、推理前向选 FP16/E4M3**：训练怕的是梯度溢出（范围优先），推理
  求的是权重精度（尾数优先）。E4M3 和 E5M2 的分工同理——NVIDIA 官方文档给的
  使用法则就是"E4M3 存前向、E5M2 存梯度"（2026-10-16 核实）。
- **FP8 不是"两个 FP16 拼一起"**，是重调偏置和码本的全新格式：E4M3 量程 ±448
  足够装激活（配合 per-tensor/per-channel scale 后），E5M2 才拿到 ±57344。
  Hopper/Ada 有原生 FP8 TensorCore，所以它在 vLLM 支持矩阵里**从 Ada 起步**
  （第 6 节），Volta/Ampere 跑 FP8 要走模拟，得不偿失。

### 3.2 INT 的存法：一把尺子（scale）和一个零点

整数没有小数点，所以量化 = 先造一把尺子：

```
对称量化:   q = clamp(round(W / s), -127, 127),   还原 W ≈ q × s
非对称量化:  q = clamp(round((W - z) / s), 0, 255), 还原 W ≈ q × s + z
```

s（scale）和 z（zero point）就是尺子的刻度和零刻度，本身也占存储——**量化省
的每一个 bit，都得从这里精打细算**。INT4 只有 16 个格子，每格间距是 INT8 的
16 倍，rounding error 天然大一个数量级——这就是"4-bit 必须带校准/优化"的
根本原因（RTN 裸四舍五入的下场见 4.1 节）。

### 3.3 粒度：一刀切、每列一把尺，还是每 128 个一把尺

| 粒度 | 做法 | 代价 | 典型 |
|---|---|---|---|
| per-tensor | 整个张量一把尺 | 元数据最少，离群值会把尺拉断，误差大 | 粗校准、KV cache |
| per-channel | 每输出通道一把尺 | 元数据 = 输出维数，精度好 | AWQ/GPTQ 惯用 |
| **per-group (g=128)** | 每 128 个权重一把尺 | 元数据 = 参数量/g，**精度/开销黄金点** | GPTQ/AWQ 默认 |
| per-token | 每个激活向量一把尺 | 需运行时动态算 scale | W8A8 推理 |

group size 是量化配置里最常出现的超参：g=128 意味着 4-bit 时每组多存 16-bit
scale，摊到 128 个权重上仅 +0.125 bit/参数，却把误差按组内分布归一——**花
0.125 个 bit 买一个数量级的误差下降**，这就是它成为默认值的原因。g=64 更精但
元数据翻倍、kernel 压力增大（QLoRA 论文选 blocksize 64 存权重、256 存 scale，
同一权衡）。

## 4. PTQ 方法地图：RTN 对照组 + 三篇论文 + 一个微调变体

训练后量化（Post-Training Quantization）不碰训练，只用少量数据（或不用车）
把已训好的权重/激活降精度。四条技术路线，按"谁最痛"排序：

### 4.1 RTN（round-to-nearest）：裸四舍五入，对照组

直接对每个权重 round 到最近的 INT4 格点。AWQ 论文 Table 1（INT3/g128，
WikiText PPL，arXiv:2306.00978v4）给它记了一笔惨案：

| 模型 | FP16 | RTN-INT3 |
|---|---|---|
| OPT-1.3B | 14.62 | **119.00** |
| OPT-6.7B | 10.86 | 23.54 |
| OPT-13B | 10.13 | 46.04 |

13B 的 PPL 从 10 飙到 46——模型没坏，是尺子太粗且所有误差毫无补偿。**这就是
一切"聪明量化方法"存在的理由：不是为了更小，是为了在同样小的时候不出错。**

### 4.2 GPTQ：给"减掉的误差"做补偿（arXiv:2210.17323，ICLR'23）

源自 Olmo/OBQ 的二阶信息（Hessian）：量化第 i 列产生的误差，用剩余未量化列
按二阶曲面**分摊补偿**回来，于是每列虽然 round 错了，后面几列会把总误差压回去。
工程三件套：① 逐层独立量化（一次只在 GPU 放一层+校准激活，128 条校准样本）；
② 低秩列分块 + Cholesky 重构，把串行依赖变成大块矩阵乘（GPU 友好）；
③ lazy batch 更新，攒几列再统一回写。

论文自报成绩（摘要原文核实，arXiv:2210.17323）：**OPT-175B 与 BLOOM-176B
约 4 个 GPU·小时**即可量化到 3/4 bit，困惑度仅"minimal increase"；此前方法在
3-4 bit 都做不到这个精度。校准集小（~128 条）且对数据分布鲁棒。
> 【请联网检索 GPTQ 论文 Table 2 的 LLaMA-7B/13B/30B/65B WikiText2 PPL
> 逐档原值】——本节刻意不给具体 PPL：两个二手转引互相矛盾（5.85 与 6.13），
> 按本书数字纪律不写入未核实数字。GPTQ 的生态位：**要自定义校准域、要最成熟的 GPU 推理
kernel（vLLM 全代际支持，第 6 节）**，选 GPTQ。

### 4.3 AWQ：保护 1% 关键通道，按"激活"找不按"权重"找（arXiv:2306.00978，MLSys'24）

观察：权重不等价——约 1% 的通道对输出影响巨大（激活分布决定，而非权重大小）。
RTN 毁掉的就是它们。AWQ 的做法不保护这些权重本身，而是给每个通道找一个缩放
s_j，在量化前把关键通道**整体放大到格点更密的区域**（量化后等比缩回），
"四两拨千斤"地保住精度。

它最漂亮的一张表（AWQ Table 1，INT3/g128，WikiText PPL）同时证明了两件事：

| 模型 | FP16 | RTN | 按激活保护 1% | 按权重大小保护 1% | 随机保护 1% |
|---|---|---|---|---|---|
| OPT-1.3B | 14.62 | 119.00 | **16.68** | 98.08 | 61.49 |
| OPT-6.7B | 10.86 | 23.54 | **11.36** | 22.45 | 24.22 |
| OPT-13B | 10.13 | 46.04 | **10.42** | 54.49 | 39.71 |

1. 按激活选：13B 从 46.04 拉回 10.42，几乎回到 FP16（10.13）；
2. 按权重大小选（行业里很流行的"保护大权重"直觉）：54.49——**几乎没用**，
   和随机选差不多。重要性由激活分布决定，不藏在权重数值里，这是 AWQ 的核心
   洞见。另：缩放因子的搜索是闭式最优的（对每个通道一维搜），无需梯度、
   校准集要求极低。

配套系统 TinyChat：on-the-fly 权重反量化 + SIMD 打包 + kernel 融合，边缘端
4-bit 相对 FP16 **3–4× 加速**——因为 decode 是访存主导，省下的字节数直接变
速度（与第 3/7 章结论互证）。生态位：**要免调参、数据高效、体积速度双优的
INT4**，AWQ 是当前消费卡/边端部署的默认选项之一。

### 4.4 SmoothQuant：把激活的"离群值税"转移给权重（arXiv:2211.10438，ICLR'23）

W8A8（权重激活都 INT8）卡在一件事上：**激活值有离群通道**（个别维度数值巨大），
激活没法像权重那样离线慢慢量化，只能一刀切 per-tensor，误差爆表。SmoothQuant
的数学平滑：

```
s_j = max|X_j|^α / max|W_j|^(1-α)   （α≈0.5）
把 W' = W/s 、X' = X×s 之后再分别量化 → 激活变规整，"难度"转移进权重
```

前后功能完全等价（对输出数学无损），却让 W8A8 变得可量化。论文成绩：最高
**1.56× 加速、2× 显存节省**，精度损失可忽略；覆盖 OPT/BLOOM/GLM/Llama-1,2/
Falcon/Mistral/Mixtral；单卡部署 OPT-175B（此前需两卡，需两卡的说法系论文
宣传口径，以原文为准）。生态位：**吞吐型服务（W8A8 让 GEMM 两个操作数都省
字节，算得也快），H100 之前的 Ampere 集群最爱**。

### 4.5 NF4：为"正态分布的权重"定制的 4-bit 码本（QLoRA，arXiv:2305.14314，NeurIPS'23）

weights 近似正态分布 → 信息论上最优的 4-bit 离散码本不是均匀的 16 格，而是
**NF4（16 个点按正态分布分位数摆放**）——均匀 INT4 在中心区浪费格子、尾部
不够用，NF4 把格子密度对准了数据密度。QLoRA 另配双重量化（scale 本身再
量化成 FP8，每参数省 0.137 bit）和 paged optimizer（长序列防 OOM）。显存账
（论文口径）：65B = 32.5 GB（4-bit）+ ~1 GB（LoRA r64）+ 激活 ≈ **48 GB
单卡可微调**。这是**微调侧**的量化——第 10 章量化实验室会亲手搭一条这样的
流水线；生产推理侧主流仍是 GPTQ/AWQ/FP8（bitsandbytes 的 NF4 主要活在
PEFT 微调里，vLLM 支持矩阵中它在 Volta→Hopper 全档可用，但定位是研究/快速
实验，第 6 节）。

### 4.6 KV Cache 量化与量化模型吞吐（预告）

权重量化管"装得下"，KV cache 量化管"撑得住并发"（第 4 章的显存账里 KV 是
可变大头）。vLLM 官方支持 Quantized KV Cache（FP8 KV 是当前标准做法），
与权重量化正交、可叠加——细节留给第 14 章并发实战。而"量化如何变成吞吐"
取决于 kernel：同一份 GPTQ 权重，Marlin kernel 比朴素实现快数倍——这就是第 7
节支持矩阵里 "Marlin (GPTQ/AWQ/FP8/FP4)" 单列一行的原因。

### 4.7 全景一张表

| 方法 | 需要校准集 | 核心动作 | 主产出精度 | 一句话定位 |
|---|---|---|---|---|
| RTN | 否 | 裸 round | 不可用（INT3/4） | 对照组 |
| GPTQ | 是（~128 条，鲁棒） | 二阶误差补偿 | W4A16 / W3 | 成熟、可自定义、kernel 广 |
| AWQ | 极少（激活统计） | 1% 通道缩放保护 | W4A16 | 免调参、体积速度双优 |
| SmoothQuant | 是 | 激活→权重难度平滑 | W8A8 | 吞吐服务、1.56× 加速 |
| NF4(bnb) | 否 | 正态分位码本 | W4 | 微调（QLoRA）专用 |

## 5. k-quants：llama.cpp 的混精工程（官方评测数据）

GGUF 的 `_K` 家族（K-quant）不搞新算法，搞的是**混合精度编码**：按张量/分块
的重要性分配不同 bit（关键层多给、冗余层少给），再配索引表。型号命名法：
`Q4_K_M` = 4-bit 主档、K 混精、M=medium（同档还有 S=small 档更小、L=large
档更精）。

llama.cpp 官方 perplexity 工具的评测表（`tools/perplexity/README.md`，
2026-10-16 抓取；CUDA backend，Wikitext-2）给了两条硬数据——

**① 当前 LLaMA 3 8B**（f16 基线 14.97 GiB / PPL 6.2332；imatrix 列 = 用
Wikitext 1000 万 token 生成的重要性矩阵）：

| 量化 | imatrix | 体积 GiB | PPL | ΔPPL | 与基线的 Mean Δp |
|---|---|---|---|---|---|
| f16 | — | 14.97 | 6.2332 | +0.0015 | 0.001% |
| q8_0 | — | 7.96 | 6.2343 | +0.0027 | -0.019% |
| q6_K | — | 6.14 | 6.2534 | +0.0217 | -0.007% |
| q5_K_M | — | 5.33 | 6.2886 | +0.0570 | -0.114% |
| **q4_K_M** | **WT 10m** | 4.58 | **6.3829** | +0.1513 | -0.389% |
| **q4_K_M** | 无 | 4.58 | 6.4071 | +0.1755 | -0.596% |
| q4_K_S | WT 10m | 4.37 | 6.4097 | +0.1781 | -0.531% |
| iq4_NL | WT 10m | 4.35 | 6.4556 | +0.2240 | -0.590% |

两个必修结论：**q8_0/q6_K 与 f16 的差异已压进不确定度区间**（+0.0027
± 0.038）——"几乎无损"不是营销词，是统计事实；**imatrix 让 q4_K_M 的 PPL
从 6.4071 降到 6.3829、KLD 降 10%**——校准矩阵在 4-bit 档是免费午餐，
3-bit 以下更是必需品（社区共识：Q3 以下不用 imatrix 必糊）。

**② 旧 LLaMA 2 70B 榜**（相对 fp16：128.5 GiB / PPL 3.4313）：

| 档位 | Q2_K | Q3_K_M | Q4_0(老) | **Q4_K_M** | Q4_1(老) | Q5_K_M | Q6_K |
|---|---|---|---|---|---|---|---|
| 体积 GiB | 27.27 | 30.83 | 36.20 | **38.54** | 40.20 | 45.41 | 52.70 |
| ΔPPL | +8.82% | +4.72% | +3.61% | **+1.20%** | +2.37% | +0.40% | +0.16% |

三个读数：**Q4_K_M 比体积更小的老式 Q4_0 还准**（+1.20% vs +3.61%，
混精编码的胜利）；Q2_K 的 8.82% 是开始"掉智"的量级；开篇那句"38.5 GiB 只差
1.2%"就来自这里。官方 caveat 必须复述：llama.cpp 的数字与其他项目**不可直接
对比**（实现细节影响结果）；困惑度本身**不是跨模型可比指标**（分词器不同），
只用于同模型量化前后对比；微调模型 PPL 常升高但人类评分反而更好。

**档位经验法则**（llama.cpp 社区通用口径 + 上表交叉）：Q8_0≈无损、Q6_K
"够用且小"、Q5_K_M 富余内存之选、**Q4_K_M 默认推荐**、Q3 以下只在极限内存
（树莓派级）或有 imatrix 时考虑；代码/医疗等对精度敏感的用途往 Q5+ 走。

## 6. 引擎支持矩阵：为什么 A 家的量化文件 B 家跑不了

格式是纸面协议，落地必须落在 kernel 上。vLLM 官方文档
（docs.vllm.ai/en/latest/features/quantization，2026-10-16 抓取）的格式与
硬件矩阵（节选，✅=支持）：

| 实现 | Volta | Turing | Ampere | Ada | Hopper | AMD | x86 CPU |
|---|---|---|---|---|---|---|---|
| AWQ | ❌ | ✅ | ✅ | ✅ | ✅ | ❌ | ✅ |
| GPTQ | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ | ✅ |
| Marlin (GPTQ/AWQ/FP8/FP4) | ❌ | ✅* | ✅ | ✅ | ✅ | ❌ | ❌ |
| FP8 W8A8 (llm-compressor) | ❌ | ❌ | ❌ | **✅** | ✅ | ✅ | ❌ |
| bitsandbytes | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ | ❌ |
| GGUF | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| INT8 W8A8 | ❌ | ✅ | ✅ | ✅ | ✅ | ❌ | ✅ |

格式列表：AutoAWQ、BitsAndBytes、GPTQModel、Intel Neural Compressor、
LLM Compressor（FP8 W8A8 / INT4 W4A16 / INT8 W4A8 / INT8 W8A8）、NVIDIA
Model Optimizer、AMD Quark、**Quantized KV Cache**、TorchAO 等；多方案混用
时用 `--linear-backend` / `linear_backend_per_quant` 指定每个方案的 kernel
后端（如 nvfp4_w4a16 用 Humming、其余 CUTLASS）。

三句人话翻译：

1. **FP8 只从 Ada 起步**——A100（Ampere）没有 FP8 TensorCore，不是软件不想
   支持，是硬件没有；Ampere 想上低精度请走 INT8（SmoothQuant 路线）。
2. **Marlin 单列一行**，因为它就是"GPTQ/AWQ 的加速器"：同一份 4-bit 权重
   换 Marlin kernel，吞吐差数倍——量化方法（文件里是什么）和 kernel（GPU 上
   怎么算）是两件事，选型时两个都要查。
3. **生态双轨**：HF/服务端 = safetensors 三兄弟（GPTQ/AWQ/FP8）；CPU/边端 =
   GGUF 单文件。国产推理栈（昇腾 MindIE、寒武纪 MagicMind）各有自己的量化
   格式与工具链，思路同构：格式 + kernel 一体（第 8 章生态表的延伸）。

【类比】量化文件像"外语录好的磁带"：格式（safetensors/GGUF）决定磁带尺寸和
卡槽，量化方法（GPTQ/AWQ）决定录音用了几种语言，播放器（vLLM/llama.cpp +
具体 kernel）决定你家机器能不能转它。三个维度各查各的表，错一个就"no
compatible kernels"。

## 7. 工程决策：把前六节串成一张选型流程

**第 1 步·按部署场景定格式与生态**：

| 你的场景 | 格式 | 量化 | 引擎 |
|---|---|---|---|
| 云上高并发服务 | safetensors | Hopper→FP8 / Ampere→INT8(W8A8) / 通用→AWQ·GPTQ | vLLM、SGLang、TensorRT-LLM |
| 消费卡跑 7B–70B 对话 | GGUF | Q4_K_M（默认）+ imatrix | llama.cpp / ollama / LM Studio |
| 边端 CPU/MCU | GGUF | Q4_K_M 及以下 + imatrix | llama.cpp |
| QLoRA 微调 | safetensors | NF4(bnb) | transformers + PEFT（第 10 章） |
| 延迟极苛刻的私有部署 | safetensors | 按目标卡的原生低精度（FP8/INT8） | 换不到 kernel 就退回 GPTQ/AWQ |

**第 2 步·按显存账定档位**（第 8 章速算器的"每参数字节"现在有了精确来源）：
7B：Q8≈8.0 / Q6≈6.0 / Q5≈5.0 / **Q4≈4.0** / Q3≈3.0 / Q2≈2.5 GiB（理论值
= bits/8 × 参数 + 分词器开销，与 llama.cpp 社区表一致）。32B bf16≈59.6 GiB
跨过 80G 单卡线（第 8 章场景二），换 4-bit 即 ~20 GiB 单卡可活——**量化在
生产里的第一价值从来不是"省流量"，是"改变架构选项"**。

**第 3 步·用第 5 节表定质量预算**：对质量敏感（代码、医疗、数学）从 Q5_K_M
起步；要"无感"上 Q6_K/Q8_0；Q4_K_M 是性价比甜点；**Q2 只属于"能跑就行"**。

**第 4 步·核对第 6 节矩阵**：目标卡代际 × 引擎 × 量化方法三者交集非空，
否则换方法不换模型。

## 8. 坑清单

1. **把格式当精度**：见 .safetensors 就以为是 fp16——GPTQ/AWQ 也是
   safetensors；打开 header 看 dtype。
2. **pickle 来源不审查直接 load**：`pytorch_model.bin` 反序列化可执行代码；
   只从可信仓库拉权重，或转 safetensors。
3. **以为 mmap 自动生效**：默认加载路径可能全量读入；用 `safe_open`/低内存
   加载，或按 I/O 实测判断。
4. **Q3 以下不配 imatrix 就上线**：官方数据显示 imatrix 在 Q4 都值 10% KLD，
   Q3 以下是"能跑"和"能用"的分界。
5. **跨模型比 PPL**：困惑度只在同模型量化前后可比（分词器不同就不可比）。
6. **A100 上找 FP8**：硬件没有该 TensorCore；Ampere 低精度正解是 INT8。
7. **量化文件和 engine 版本硬凑**：格式新、kernel 旧会直接拒绝加载；
   先查支持矩阵再下模型。
8. **拿 llama.cpp 的 PPL 和别的项目比**：官方明确声明不可直接比。
9. **只压权重不看 KV**：并发是 KV 主导（第 4 章），FP8 KV cache 是另一半
   显存战场（第 14 章）。
